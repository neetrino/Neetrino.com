## 1. Role of this file

This file is the authoritative on-page SEO and content-optimization reference for the Neetrino SEO Blog GPT. Use it after a page has an approved audience, intent, canonical role, brief, outline, and editorially verified draft, and whenever an existing page is reviewed, refreshed, consolidated, localized, migrated, or prepared for publication.

It defines:

- how to verify that one page satisfies one dominant search task without competing with another owner;
- how to align the search title, H1, slug, meta description, opening, headings, body, links, media, CTA, and structured data;
- how to use primary queries, variants, terminology, entities, relationships, and supporting questions without keyword stuffing;
- how to improve extractable answers, featured-snippet eligibility, AI-search usefulness, and zero-click brand value;
- how to optimize internal links, anchors, inbound support, citations, images, tables, lists, and other structured elements;
- how to distinguish content optimization from editorial rewriting and technical SEO implementation;
- how to govern canonical, indexation, localization, duplicate, merge, split, redirect, and migration implications at page level;
- how to document optimization decisions, evidence, changes, blockers, implementation needs, and measurement baselines;
- how to validate both the proposed publication package and the rendered page.

This file does not discover topics from scratch, replace live keyword or SERP research, assign cluster ownership without portfolio review, repair crawl infrastructure, guarantee rankings, invent schema-supported facts, or override editorial accuracy. Those responsibilities remain with their canonical systems.

## 2. Core operating principle

On-page optimization makes a verified page easier to understand, retrieve, select, navigate, and use. It must improve the match between the reader's task, the page's promise, its evidence, and its machine-readable implementation without making the content less natural, accurate, differentiated, or useful.

Use this chain:

> verified page purpose → current search evidence → ownership check → promise alignment → semantic completeness → useful answer structure → link and media support → eligible machine-readable signals → rendered validation → measured learning

Optimize meaning before wording, usefulness before repetition, and the full page system before isolated fields. A keyword appearing seven times is not seven units of relevance.

## 3. Required conceptual distinctions

### 3.1 On-page SEO

The page-level alignment of visible content, metadata, semantic signals, links, media, and eligible structured data with a defined reader task and search interpretation.

### 3.2 Content optimization

A change to an existing draft or page intended to improve usefulness, clarity, completeness, differentiation, retrieval, navigation, conversion continuity, or maintenance. It may include substantive editorial changes and therefore requires appropriate review.

### 3.3 Technical SEO

Site or platform conditions affecting crawling, rendering, indexing, canonicalization, performance, internationalization, structured-data delivery, and URL behavior. This file records page-level requirements and defects but does not replace a technical SEO system.

### 3.4 Primary query cluster

A group of searches expressing materially the same dominant task and suitable for one canonical page. It is not every phrase that contains the topic word.

### 3.5 Supporting query

A related question, subtask, modifier, entity, risk, comparison, or implementation need that strengthens the primary page when it fits the promise. A supporting query may instead require another owner.

### 3.6 Search title

The title supplied for search and sharing systems, commonly through the HTML title element. It may differ from the H1 but must communicate the same core promise.

### 3.7 H1

The primary visible page heading. It establishes the page's human-readable subject and promise within the rendered experience.

### 3.8 Meta description

A concise, accurate summary or invitation associated with the page. It may influence selection but is not a guaranteed search-result snippet or a place for unsupported claims.

### 3.9 Semantic coverage

Coverage of the entities, attributes, relationships, terminology, subquestions, and distinctions necessary to fulfil the page promise. It is not the automated insertion of related words.

### 3.10 Information gain

Useful value beyond generic restatement: stronger synthesis, clearer decision logic, verified evidence, practical examples, original experience, local context, templates, trade-offs, or a better explanation.

### 3.11 Answer unit

A concise passage, list, table, definition, or step sequence that answers one meaningful question accurately and remains understandable when surfaced with limited surrounding context.

### 3.12 Structured data

Machine-readable markup describing content and entities that actually exist on the rendered page. It does not create eligibility, authority, reviews, FAQs, services, authors, or events that the page itself does not support.

### 3.13 Canonical owner

The preferred page responsible for satisfying a defined dominant task in a defined language and market. Canonical markup cannot repair ambiguous editorial ownership by itself.

### 3.14 Optimization evidence

The documented basis for a proposed change: live SERP observation, verified query data, search-console data, analytics, user behavior, site-search data, support or sales evidence, content audit findings, or an established accessibility or implementation requirement.

## 4. Authority and dependency order

When instructions conflict, use this order:

1. verified facts, legal obligations, safety, privacy, accessibility, and platform constraints;
2. approved reader need, search intent, page ownership, and business objective;
3. canonical Neetrino brand, service, audience, proof, and factual-owner files;
4. approved content-gap, cluster, brief, and page-plan decisions;
5. approved information architecture and editorially verified draft;
6. current keyword, SERP, performance, and user evidence;
7. this on-page optimization system;
8. conversion, design, development, technical SEO, publishing, and measurement systems;
9. task-specific preferences that do not violate higher authorities.

Never change an accurate claim, approved page promise, canonical owner, or user-critical caveat merely to imitate a search result. Escalate the conflict.

## 5. Minimum inputs before optimization

Do not claim full optimization readiness without:

- page URL or proposed slug;
- language, market, and locale;
- page type, cluster, canonical owner, and neighboring owners;
- primary audience, reader task, dominant intent, and journey stage;
- approved page promise and CTA path;
- editorially verified draft or live rendered page;
- approved primary query cluster and meaningful supporting needs;
- current SERP evidence when a search-facing recommendation depends on it;
- known performance evidence for an existing page;
- verified sources, claims, author or reviewer data, dates, and media rights;
- implementation constraints for title, metadata, canonical, hreflang, schema, links, and CMS fields;
- measurement baseline and accountable owner when optimization affects a live page.

If inputs are missing, mark recommendations `provisional`, `blocked`, or `requires research`. Do not turn uncertainty into confident metadata.

## 6. Optimization lifecycle and states

| State | Meaning | Permitted action |
| --- | --- | --- |
| Requested | Page entered review | Gather inputs |
| Diagnosing | Evidence and ownership are being checked | Record findings; no final claim |
| Provisional | Direction exists but depends on unresolved evidence | Draft alternatives and label assumptions |
| Approved | Strategy and material changes are authorized | Prepare implementation package |
| Implementing | Changes are being placed in the CMS or code | Preserve approved meaning |
| Rendered QA | Live or preview output is available | Validate actual behavior |
| Ready | Required checks pass | Publish or release |
| Published | Canonical version is live | Record baseline and monitor |
| Measuring | Sufficient post-change data is accumulating | Avoid premature reversal |
| Refresh due | Evidence or freshness threshold requires review | Re-diagnose |
| Blocked | A material dependency is unresolved | Do not label ready |
| Rejected | Proposed change lacked benefit or violated authority | Preserve rationale |

Optimization is not complete when a spreadsheet field is filled. It is complete when the intended change renders correctly and the record identifies what should be measured.

## 7. Optimization modes and scope

### 7.1 New-page optimization

Finalize the publication package from the approved draft. Confirm ownership, metadata, URL, internal links, inbound support, media, schema eligibility, tracking, and indexation before launch.

### 7.2 Metadata-only optimization

Change titles or descriptions only when the visible page already fulfils the same promise. If metadata promises value the page does not deliver, update the page or reduce the promise.

### 7.3 Content refresh

Update stale facts, examples, screenshots, dates, links, steps, evidence, and current terminology while preserving valid ownership and accumulated value.

### 7.4 Intent realignment

Use when current evidence shows that the page targets the wrong task, format, or audience state. This is a material strategy change requiring brief and ownership review.

### 7.5 Consolidation

Merge competing or fragmented assets into one stronger owner, preserve unique value, update links, and define redirects and measurement.

### 7.6 Localization optimization

Optimize the localized reader task and search language rather than translating keyword placement mechanically.

### 7.7 Recovery optimization

Diagnose a performance decline before editing. Separate content decay, SERP change, intent change, technical defects, seasonality, migration loss, link loss, and measurement error.

## 8. Search alignment review

Evaluate alignment across these fields:

| Element | Required alignment |
| --- | --- |
| Canonical owner | Owns one defined dominant task |
| Page type | Matches what the task requires |
| Search title | States the useful promise clearly |
| H1 | Expresses the same promise naturally |
| Opening | Confirms relevance and begins the answer |
| Headings | Expose the task sequence and supporting needs |
| Body | Delivers the promised depth and evidence |
| Media | Helps explain, prove, compare, or act |
| Internal links | Connect prerequisites and next decisions |
| CTA | Fits reader readiness and page role |
| Schema | Describes visible eligible content |

If these elements imply different intents, stop polishing phrases and resolve the page's purpose.

Classify alignment as:

- `direct` — the page clearly owns and satisfies the task;
- `supporting` — the term belongs as a subordinate need;
- `adjacent` — relevant context with another canonical owner;
- `misaligned` — the page type, promise, or reader state is wrong;
- `unknown` — evidence is insufficient.

## 9. Page ownership and cannibalization control

Before optimization:

1. Identify the primary query cluster and reader task.
2. Search the site inventory for pages with the same or confusingly similar promise.
3. Compare page type, audience, journey stage, scope, title, H1, anchors, rankings, and internal links.
4. Identify the intended owner and the role of every neighbor.
5. Choose keep distinct, reposition, merge, split, redirect, canonicalize, noindex, or retire.
6. Update the cluster and page-ownership records before materially retargeting a page.

Do not diagnose cannibalization from shared keywords alone. Diagnose ambiguous ownership when pages compete for the same task, receive conflicting internal signals, alternate unpredictably, or duplicate the same promise without independent value.

## 10. Search-title system

### 10.1 Required properties

A search title should:

- identify the subject or task quickly;
- express the page's distinct useful outcome;
- match the dominant intent and page type;
- use language natural to the target market;
- differentiate honestly when evidence supports it;
- remain understandable when shown without the site navigation;
- preserve important qualifiers such as audience, platform, location, year, or comparison direction only when materially relevant;
- avoid duplicate or near-duplicate titles across indexable pages.

### 10.2 Composition

Possible components include:

> primary task or subject + meaningful qualifier + useful outcome or page type + brand when appropriate

This is a decision model, not a fixed template. Put the clearest information first. Do not add a year, number, superlative, question, bracket, or brand suffix merely because a tool scores it higher.

### 10.3 Length

No universal character count guarantees display. Optimize for clarity and front-loaded meaning, then preview likely truncation. Preserve critical meaning even when the tail is omitted.

### 10.4 Search title and H1

They may differ when the search context benefits from a concise qualifier and the visible page benefits from more natural wording. They must not target different intents or make different claims.

### 10.5 Title alternatives record

For every material alternative, record:

- proposed title;
- intended task and differentiator;
- evidence;
- risk or trade-off;
- selected status and rationale.

## 11. H1 and visible-title system

Use one primary visible heading that:

- makes the page subject and promise unmistakable;
- fits the natural syntax of the page language;
- matches the actual content and reader state;
- is not hidden, replaced by an image, or visually confused with decorative text;
- avoids copying a generic query when a clearer human title is available.

Multiple technical H1 elements may render without an immediate ranking penalty, but they often weaken semantic and accessibility clarity. Use one intentional H1 unless the component architecture has a documented, tested reason otherwise.

## 12. URL and slug standards

Prefer URLs that are:

- concise, readable, stable, and lowercase where the system permits;
- descriptive of the canonical subject rather than the current campaign;
- free from unnecessary dates, tracking parameters, internal IDs, stop-word clutter, and repeated folder names;
- localized according to an approved market convention;
- consistent with the site's information architecture.

For an existing useful URL, preserve it unless a documented migration benefit exceeds redirect, link, analytics, indexing, and operational risk. A prettier slug is rarely worth erasing a known address.

When changing a URL, require:

- exact old and new URL;
- one-hop permanent redirect plan;
- canonical, sitemap, navigation, hreflang, structured-data, and internal-link updates;
- external-link outreach only when material;
- analytics annotation and post-launch validation;
- rollback owner.

## 13. Meta-description standards

A meta description should:

- summarize the actual page promise;
- indicate useful scope, outcome, or decision support;
- use natural language and a proportionate invitation;
- include important terminology only when it reads naturally;
- avoid claims, prices, dates, or availability that may become false;
- differ across distinct indexable pages;
- remain meaningful if the search engine selects another snippet.

Do not stuff variants, repeat the title, use empty urgency, or write a sales CTA for an informational page. Treat length as a display constraint to preview, not a ranking formula.

## 14. Opening and primary-answer alignment

The opening must confirm that the visitor reached the right page and begin satisfying the task.

Within the first useful screen or early passage, establish as appropriate:

- the direct answer or governing recommendation;
- the definition or scope when ambiguity exists;
- who the guidance is for;
- the main condition, caveat, or trade-off;
- what the page will help the reader decide or do.

Do not add a generic history, inflated trend claim, dictionary preamble, or keyword-loaded throat-clearing merely to delay the answer.

## 15. Heading optimization

Headings should reveal the information hierarchy and help both scanning and retrieval.

Requirements:

- one distinct job per section;
- semantic nesting rather than visual level selection;
- natural labels that communicate the reader question or outcome;
- query language where it improves recognition, not where it damages clarity;
- no duplicate headings that repeat the same answer;
- no heading inserted solely to place a variant;
- no leap in level unless the component semantics require and document it.

Review headings as a standalone outline. If they read like a list of related keywords rather than a journey, the structure remains unresolved.

## 16. Query and terminology coverage

### 16.1 Placement priorities

Use the clearest natural terminology in the search title, H1, opening, relevant headings, body, links, and media fields when each location performs a legitimate function. Exact-match repetition is not required.

### 16.2 Variants

Include variants when they:

- are the natural vocabulary of different reader groups;
- disambiguate a concept;
- name a recognized alternative, acronym, product, standard, or local term;
- support a distinct question answered on the page.

Do not create sentences, FAQs, captions, or alt text only to host variants.

### 16.3 Keyword density

Do not target a fixed density. Review unnatural repetition, missing terminology, ambiguous pronouns, and incomplete concept relationships instead.

### 16.4 Term mapping

Maintain a term record when terminology is complex:

| Concept | Preferred audience term | Accepted variant | Technical term | Language/market note | Use or avoid |
| --- | --- | --- | --- | --- | --- |

## 17. Entity and semantic coverage

Identify only entities necessary to fulfil the promise:

- products, services, organizations, industries, roles, technologies, standards, locations, processes, risks, metrics, and outcomes;
- attributes that distinguish them;
- relationships among them;
- conditions under which a relationship changes;
- evidence that supports the relationship.

For every candidate entity, ask:

1. Does the reader need it to understand or act?
2. Is it within page scope?
3. Is the relationship accurate and verified?
4. Does another page own the deeper explanation?
5. Can it be named naturally without list-like insertion?

An entity list from an optimization tool is a diagnostic input, not a mandatory vocabulary sheet.

## 18. Topical completeness and information gain

A page is complete when it fulfils its defined promise, not when it covers the entire topic universe.

Assess:

- direct answer completeness;
- prerequisite understanding;
- decision criteria;
- meaningful alternatives;
- evidence, limitations, and uncertainty;
- implementation or next-step support;
- local, industry, or role-specific context;
- distinct Neetrino experience or synthesis;
- routes to canonical deeper pages.

Information gain may come from:

- verified first-party experience or data;
- a clearer framework or decision tree;
- a worked example with stated assumptions;
- a local-market or multilingual perspective;
- explicit trade-offs and failure modes;
- a reusable checklist, template, comparison, or calculation;
- synthesis that connects evidence without overstating it.

Do not invent novelty. “Unique” unsupported claims are generic marketing wearing a bright tie.

## 19. Content depth, length, and pruning

Use the minimum depth required to answer the task responsibly.

Expand when the page lacks:

- a required distinction, condition, evidence, example, step, risk, or decision criterion;
- enough context for the intended audience;
- a useful answer to a validated supporting need.

Prune or externalize when content:

- repeats an earlier answer;
- belongs to another canonical owner;
- exists only for phrase coverage;
- is outdated, weakly evidenced, or off-journey;
- adds detail disproportionate to the reader task;
- delays the answer or CTA without increasing trust or decision quality.

Never set word count from competitor averages alone. Similar length does not imply similar usefulness.

## 20. Answer units and passage-level usefulness

Build answer units where the page contains a meaningful question that benefits from concise resolution.

Each answer unit should:

- state the subject explicitly;
- answer before elaborating;
- preserve essential qualifiers;
- use a format appropriate to the task;
- connect to supporting evidence or detail;
- remain accurate when read with limited surrounding context;
- avoid promotional interruption.

Suitable forms include a short paragraph, definition, numbered steps, comparison table, checklist, formula, example, or decision rule.

Do not fragment every paragraph into “snippet bait.” The full page still needs continuity.

## 21. Featured-snippet readiness

Use current SERP evidence before targeting a featured format. Determine whether the result surface favors a paragraph, list, table, steps, calculation, video, image, or another form.

Then:

- place a precise question or descriptive heading near the answer;
- provide the answer directly in the format that best serves the reader;
- make labels and step order unambiguous;
- retain caveats required for accuracy;
- support the concise answer with deeper evidence below.

Do not copy a competitor's wording, distort an answer to fit a guessed length, or promise snippet acquisition. Eligibility is not control.

## 22. AI-search and answer-surface readiness

Optimize for citation-worthy usefulness, not for speculative model preferences.

Prioritize:

- clear entity references and relationships;
- concise answers with preserved conditions;
- verifiable claims and accessible sources;
- visible author, reviewer, organization, date, and update context where relevant;
- original evidence, examples, frameworks, and first-party experience;
- stable headings and linkable sections;
- consistent facts across related pages and languages;
- machine-readable markup that matches visible content;
- a clear route from a surfaced answer to deeper value or action.

Zero-click usefulness can still create value through accurate brand association, later direct navigation, citations, trust, and assisted conversion. Record these as hypotheses unless measured.

Do not write for an imaginary AI crawler at the expense of a human reader.

## 23. Internal-link optimization

Every internal link must perform a legitimate function:

- prerequisite explanation;
- deeper canonical treatment;
- evidence or case support;
- comparison or alternative;
- next journey step;
- service or conversion destination;
- cluster or hub navigation;
- recovery from an obsolete or consolidated route.

Use this record:

| Source section | Destination owner | Link purpose | Suggested anchor direction | Existing/proposed | Verification |
| --- | --- | --- | --- | --- | --- |

Requirements:

- link to the canonical live destination, not a duplicate or redirected URL;
- place the link where the reader needs it;
- use descriptive surrounding context;
- keep the number proportionate to page tasks;
- update links after merges, migrations, localization, or URL changes;
- verify access, language, status, and final destination.

## 24. Anchor-text standards

Anchor text should describe the destination's useful subject in the natural sentence context.

Use:

- concise descriptive phrases;
- meaningful partial-match or task language;
- branded or navigational wording where appropriate;
- varied wording only when the surrounding meaning genuinely differs.

Avoid:

- repeated exact-match anchors inserted mechanically;
- “click here,” bare URLs, or context-free “learn more” when a better label is possible;
- anchors promising information absent from the destination;
- overly long anchors that absorb an entire paragraph;
- localized anchors pointing to the wrong language without clear reason.

## 25. Inbound-link requirements

A new or materially repositioned page is not integrated until relevant existing pages link into it.

Identify:

- parent pillar or hub;
- relevant service and industry pages;
- supporting articles and glossary pages;
- case studies, resources, and comparison pages;
- navigation, breadcrumbs, or related-content modules when appropriate;
- localized equivalent and alternate-market routes.

Record the exact source owner and implementation status. “Add internal links later” is not a launch plan.

## 26. External links and citations

Use external links when they help the reader verify, interpret, or act on material information.

Prefer:

- primary sources, official documentation, standards, regulators, original research, and directly relevant evidence;
- stable destinations that support the exact claim;
- descriptive context and appropriate citation proximity.

Check:

- source authority and date;
- claim-to-source fit;
- conflicts of interest;
- access barriers;
- link status;
- quotation and licensing limits;
- whether a source is required even if an outbound link is commercially inconvenient.

Do not remove useful citations to “keep authority on the page.” Trust is not a fluid that leaks through hyperlinks.

## 27. Images and media optimization

Every image, diagram, video, audio item, chart, screenshot, or downloadable asset must have a defined job.

### 27.1 Selection

Use media to explain, prove, compare, orient, demonstrate, or enable action. Avoid decorative assets that delay load, compete with the answer, or imply unverified results.

### 27.2 File and delivery requirements

Record:

- descriptive, stable filename when feasible;
- appropriate format, dimensions, compression, and responsive variants;
- intrinsic size to reduce layout shift;
- lazy-loading behavior except when it harms the primary above-the-fold asset;
- rights, attribution, source, and update owner;
- transcript, captions, or text alternative when required.

### 27.3 Alternative text

Alt text must communicate the image's relevant purpose or content to a user who cannot see it.

- Describe informative images concisely in context.
- Use empty alt text for truly decorative images.
- For complex visuals, provide a short alt plus an adjacent detailed explanation or data table.
- Do not repeat nearby captions unnecessarily.
- Do not place keywords unrelated to the image.

### 27.4 Captions and surrounding text

Use captions when provenance, interpretation, caveat, time, location, or result context matters. The surrounding text should explain why the media is relevant rather than merely naming it.

## 28. Tables, lists, definitions, and structured components

Choose structure by task:

| Reader task | Preferred component |
| --- | --- |
| Compare consistent attributes | Table |
| Follow ordered actions | Numbered steps |
| Check unordered criteria | Bulleted checklist |
| Understand one term | Concise definition |
| Choose among conditions | Decision table or flow |
| Apply a repeatable method | Template or worksheet |
| Inspect quantitative relationship | Chart with accessible data |

Requirements:

- introduce the component and its scope;
- use explicit labels and units;
- keep mobile readability and accessibility;
- preserve important caveats near the data;
- ensure values and claims are sourced;
- avoid converting prose into a list solely for snippet appearance.

## 29. Structured-data eligibility

Recommend structured data only when:

- the page and visible content match the schema type;
- all required properties are present and verified;
- recommended properties add truthful context;
- the markup reflects the canonical rendered page;
- implementation can be tested and maintained;
- current search-platform guidelines have been checked when eligibility matters.

Possible types depend on the actual page and may include organization, website, breadcrumb, article, person, service, product, review, FAQ, how-to, video, software application, event, local business, or dataset markup. Naming a type here does not authorize it.

Never:

- mark up invisible or AI-invented content;
- manufacture reviews, ratings, prices, availability, authors, questions, steps, locations, or dates;
- use FAQ markup for keyword variants that are not genuine visible questions;
- assume valid markup guarantees a rich result;
- stack conflicting types without a coherent entity model.

The implementation record must include eligible type, rationale, visible source fields, required properties, owner, validator result, and maintenance trigger.

## 30. Canonical, indexation, and duplicate control

### 30.1 Canonical intent

Record the preferred URL for the content. Confirm that self-referencing or cross-URL canonical behavior matches the ownership decision.

### 30.2 Indexation intent

Choose `index`, `noindex`, consolidation, redirect, access control, or removal based on page value and ownership—not as a shortcut around unresolved duplication.

### 30.3 Duplicate and parameter risks

Review:

- HTTP/HTTPS and host variants;
- trailing slash and case behavior;
- query parameters, filters, sort states, print views, previews, and tracking URLs;
- pagination and faceted navigation;
- syndicated or republished content;
- staging and test environments;
- translations and regional equivalents;
- PDF and HTML duplicates;
- campaign copies and tag archives.

Canonical is a signal, not a permission slip to maintain a confusing page portfolio.

## 31. Localization and multilingual on-page SEO

For Armenian, English, and Russian versions:

- validate the local audience task and natural search language;
- localize titles, H1s, descriptions, slugs, headings, examples, CTAs, anchors, media text, and structured fields;
- preserve factual and strategic equivalence without literal phrase order;
- map each version to the correct canonical owner in its market;
- define hreflang or alternate relationships through the technical implementation system;
- ensure language selectors preserve the equivalent destination where one exists;
- avoid sending users to a homepage when a localized equivalent is available;
- document missing equivalents rather than inventing them;
- maintain the same claim confidence and source integrity across languages.

Do not mix visible metadata languages except for approved names and technical terms. Do not assume the highest-volume English phrasing has a direct Armenian or Russian equivalent.

## 32. Service, comparison, case, how-to, and technical pages

### 32.1 Service pages

Align service, audience problem, scope, outcomes, process, proof, limitations, qualification, and CTA. Avoid replacing clear service language with broad informational coverage better owned by a guide.

### 32.2 Comparison pages

State the comparison basis, audience, criteria, evidence, conditions, and recommendation logic. Use consistent attributes and avoid declaring a universal winner without context.

### 32.3 Case studies

Make client context, challenge, intervention, timeframe, result, metric definition, attribution limits, and permissions explicit. Do not optimize an anecdote into a guaranteed outcome.

### 32.4 How-to pages

Define prerequisites, ordered steps, decisions, warnings, validation, and expected result. Structured data is optional and eligibility-dependent; procedural usefulness is mandatory.

### 32.5 Technical pages

Preserve versions, environments, dependencies, commands, security implications, error states, and verification. Use code and screenshots only when current and reproducible.

## 33. Conversion and SEO alignment

The conversion path must follow the reader's readiness.

| Reader state | Suitable next step |
| --- | --- |
| Learning | Related explanation, checklist, or glossary |
| Diagnosing | Assessment, requirements guide, or example |
| Comparing | Criteria, case evidence, consultation, or estimate inputs |
| Planning | Scope template, architecture review, or implementation guide |
| Ready to act | Relevant service CTA, contact, booking, or proposal path |

Requirements:

- preserve the informational answer before the commercial ask;
- link to the canonical conversion destination;
- use CTA language consistent with actual process and availability;
- avoid hiding useful answers behind a form merely to increase leads;
- track meaningful actions without claiming ranking causality.

## 34. Trust, authorship, and transparency signals

Where relevant, make visible:

- author and qualified reviewer;
- organization and applicable experience;
- publication and material-update dates;
- sources and methodology;
- assumptions, limitations, conflicts, sponsorship, and affiliate relationships;
- client permissions and anonymization status;
- contact, correction, or editorial policy routes.

Do not add credentials, review labels, or update dates that do not correspond to real work. Fresh date paint does not make old guidance fresh.

## 35. Accessibility and rendered usability

On-page SEO changes must preserve or improve:

- semantic headings and landmarks;
- keyboard and focus behavior;
- descriptive links;
- image alternatives;
- captions and transcripts;
- table headers and reading order;
- color contrast and non-color cues;
- readable labels, error messages, and form instructions;
- zoom, reflow, and responsive behavior;
- language attributes and pronunciation clarity where supported.

Accessibility is a quality input, not an optional post-optimization repair.

## 36. Mobile and page-experience considerations

Validate the rendered page on representative mobile widths and realistic connections.

Check:

- the promise and primary answer are not buried below intrusive elements;
- title, navigation, table of contents, tables, code, media, and CTAs remain usable;
- overlays and consent interfaces do not block the task;
- images reserve space and load appropriately;
- accordions do not hide critical conditions;
- tap targets and links remain distinguishable;
- performance changes are measured with suitable field and lab evidence;
- optimization tools or scripts do not create layout or interaction defects.

Do not make unsupported Core Web Vitals or ranking claims from one laboratory run.

## 37. Update, merge, split, and migration optimization

### 37.1 Update

Preserve valid URLs, strong sections, links, evidence, and point of view. Record obsolete material, new evidence, changed intent, and material date updates.

### 37.2 Merge

Choose the surviving owner from evidence, not convenience. Preserve unique useful content, rebuild one coherent narrative, redirect retired URLs, update inbound links, and remove contradictory metadata.

### 37.3 Split

Create separate pages only for distinct tasks with independently useful promises. Allocate sections, queries, links, titles, and CTAs explicitly and prevent the source page from continuing to compete.

### 37.4 Migration

Create a URL map, metadata map, canonical and hreflang plan, redirect rules, internal-link updates, sitemap changes, analytics annotation, crawl validation, and rollback ownership.

## 38. Optimization severity and change control

| Severity | Definition | Examples | Approval |
| --- | --- | --- | --- |
| S0 — Formatting | No meaning or search-target change | spacing, broken list, alt punctuation | Editor or publisher |
| S1 — Minor | Clearer expression within approved intent | title refinement, anchor improvement, redundancy removal | SEO/editor owner |
| S2 — Material | Changes scope, evidence, section structure, CTA, or semantic emphasis | new section, substantive pruning, schema addition | SEO + editorial/SME as relevant |
| S3 — Strategic | Changes owner, intent, page type, URL, canonical, indexation, merge, or split | retargeting, migration, consolidation | Strategy + technical + business owner |
| S4 — Critical | Legal, safety, privacy, security, factual, or severe accessibility risk | false claim, exposed data, harmful instruction | Stop publication; accountable authority |

For S2–S4, record the old state, proposed state, evidence, risks, dependencies, approver, implementation status, and rollback or recovery path.

Do not silently rewrite an approved page under the label “SEO edit.”

## 39. AI-assisted optimization rules

AI may assist with:

- inventorying titles, headings, terms, entities, links, media fields, and schema candidates;
- clustering already validated query variants;
- identifying possible omissions, repetition, ambiguity, broken alignment, and duplicate promises;
- drafting labelled title, description, anchor, answer-unit, or component alternatives;
- comparing a draft against an approved brief and checklist;
- preparing implementation records and QA test cases.

AI must not:

- invent volume, rankings, traffic, SERP features, competitor behavior, or performance;
- infer search-platform rules as permanent facts;
- create unsupported claims, reviews, authors, experience, citations, dates, or schema fields;
- rewrite expert meaning without review;
- add keywords or entities because a tool listed them;
- declare a page optimized, eligible, indexed, or ranking without validation;
- perform a material ownership, URL, canonical, noindex, redirect, or merge decision without approval.

Every AI-originated factual or strategic suggestion requires the same verification as a human-originated suggestion.

## 40. Implementation handoff

The implementation package must separate content decisions from platform actions.

Include:

- final search title, H1, slug, and meta description;
- canonical and indexation intent;
- language and alternate-page relationships;
- final heading and content changes;
- internal outbound and required inbound links;
- external citations;
- media files, alt text, captions, transcripts, rights, and responsive requirements;
- structured-data type, source fields, and eligibility rationale;
- redirects and URL maps;
- breadcrumb, navigation, table-of-contents, and component requirements;
- analytics events and baseline;
- preview URL, validator requirements, owner, approver, and release status.

Mark every destination and asset as `verified live`, `approved planned`, `blocked`, or `not applicable`.

## 41. Validation and evidence protocol

Validation has four layers.

### 41.1 Strategy validation

- audience, task, intent, page role, and owner agree;
- research is current enough for the decision;
- neighboring pages remain distinct;
- the CTA follows the journey.

### 41.2 Editorial validation

- title, H1, opening, headings, body, media, and conclusion make the same promise;
- claims and sources remain accurate;
- optimization did not damage voice, clarity, accessibility, or originality;
- semantic coverage is useful rather than mechanical.

### 41.3 Implementation validation

- fields render in the intended language;
- canonical, robots, redirects, hreflang, schema, links, and media are correct;
- no preview, staging, parameter, or duplicate route creates conflict;
- mobile, accessibility, and interaction behavior pass.

### 41.4 Search validation

- the final URL is reachable and intended for discovery;
- search tools can render the primary content where authorized;
- sitemap and internal discovery paths are correct;
- indexing and enhancement reports are monitored after launch;
- performance conclusions use a suitable comparison period and account for confounders.

Never claim causality from a single before-and-after observation.

## 43. On-page quality score

Score each criterion `0`, `1`, or `2`:

- `0` — missing, unsupported, conflicting, or materially defective;
- `1` — present but incomplete, provisional, or needing improvement;
- `2` — verified, coherent, implemented, and fit for purpose.

| # | Criterion | Score |
| --- | --- | --- |
| 1 | Audience and reader-task alignment | 0–2 |
| 2 | Dominant intent and page-type fit | 0–2 |
| 3 | Canonical ownership and differentiation | 0–2 |
| 4 | Search-title quality | 0–2 |
| 5 | H1 and visible-promise alignment | 0–2 |
| 6 | URL stability and clarity | 0–2 |
| 7 | Meta-description accuracy | 0–2 |
| 8 | Opening and primary-answer usefulness | 0–2 |
| 9 | Heading and passage structure | 0–2 |
| 10 | Query and terminology naturalness | 0–2 |
| 11 | Entity and semantic completeness | 0–2 |
| 12 | Information gain and evidence | 0–2 |
| 13 | Internal outbound links | 0–2 |
| 14 | Required inbound links | 0–2 |
| 15 | External citations and trust | 0–2 |
| 16 | Media purpose and accessibility | 0–2 |
| 17 | Structured-data integrity | 0–2 |
| 18 | Canonical, indexation, and localization integrity | 0–2 |
| 19 | Conversion-path fit | 0–2 |
| 20 | Rendered mobile and accessibility QA | 0–2 |

Maximum: `40`.

Interpretation:

- `36–40` — ready if no blocker or mandatory zero exists;
- `30–35` — strong but requires documented corrections;
- `22–29` — material optimization work remains;
- `0–21` — not ready; revisit strategy, content, or implementation.

Mandatory zeros that block readiness:

- factual or legal integrity;
- dominant intent or canonical ownership;
- title/page promise alignment;
- canonical or indexation intent;
- material accessibility or rendering defect;
- fabricated evidence or structured data.

A high total cannot average away a critical failure.

## 45. Anti-patterns

Reject optimization that:

- starts from a keyword list without a reader task or canonical owner;
- repeats exact phrases to reach a density score;
- adds every tool-suggested entity, question, or competitor heading;
- copies SERP titles, outlines, definitions, or snippet wording;
- changes the URL for cosmetic reasons without a migration plan;
- makes the title more dramatic than the page evidence;
- uses an H1, title, and opening for three different intents;
- creates FAQ blocks solely for variants or schema;
- adds a year without maintaining the content;
- updates the date without a material review;
- inflates word count to match competitors;
- removes useful citations or caveats for concision;
- converts natural prose into isolated answer fragments everywhere;
- treats internal-link quantity as authority;
- uses exact-match anchors mechanically;
- links to redirects, duplicates, wrong languages, or future pages marked as live;
- stuffs alt text or filenames;
- marks up hidden, invented, or ineligible structured data;
- uses canonical or noindex to avoid deciding content ownership;
- translates metadata literally across markets;
- hides essential content in inaccessible components;
- promises featured snippets, rich results, AI citations, indexing, or rankings;
- declares success immediately after publication;
- attributes every performance change to the latest edit;
- labels a page “fully optimized” when blockers remain.

## 46. Pre-publication checklist

### Strategy and ownership

- [ ] The page has one defined audience task, dominant intent, page role, and canonical owner.
- [ ] The page type matches the task.
- [ ] Neighboring pages have distinct promises or an approved consolidation plan.
- [ ] Current search evidence supports material search-facing decisions.
- [ ] The CTA matches journey readiness.

### Titles, URL, and metadata

- [ ] Search title, H1, opening, headings, body, and CTA make the same core promise.
- [ ] The search title is clear, differentiated, natural, and not duplicated.
- [ ] The H1 is visible, semantic, and human-readable.
- [ ] The slug is stable, concise, and appropriate to the language and architecture.
- [ ] Any URL change has an approved redirect and migration plan.
- [ ] The meta description accurately summarizes the page without unsupported claims.

### Content and semantics

- [ ] The primary answer appears early enough for the task.
- [ ] Headings expose a coherent information journey.
- [ ] Primary terminology and useful variants appear naturally.
- [ ] Required entities and relationships are accurate and sufficiently explained.
- [ ] Supporting questions fit the page scope.
- [ ] The page adds useful evidence, synthesis, examples, or decision support.
- [ ] Repetition, filler, stale content, and material owned elsewhere are removed or routed.
- [ ] Answer units preserve essential caveats.

### Links, evidence, and conversion

- [ ] Internal outbound links serve explicit reader functions and use canonical live destinations.
- [ ] Required inbound links have exact source owners and implementation status.
- [ ] Anchor text is descriptive and natural.
- [ ] External citations support the precise claims and remain accessible.
- [ ] CTA destinations, labels, and expectations are accurate.

### Media and components

- [ ] Every media asset has a useful role, rights status, owner, and update need.
- [ ] Filenames, formats, dimensions, compression, and responsive behavior are suitable.
- [ ] Alt text, captions, transcripts, and complex-visual explanations are correct.
- [ ] Tables, lists, code, charts, and interactive components remain usable on mobile and assistive technology.

### Machine-readable and international signals

- [ ] Canonical and indexation intent match page ownership.
- [ ] Duplicate, parameter, preview, staging, and alternate-format risks are addressed.
- [ ] Localized metadata, links, CTAs, and equivalent-page relationships are correct.
- [ ] Structured data, if used, describes visible eligible content with verified properties.
- [ ] Breadcrumb, navigation, sitemap, hreflang, and redirect requirements are handed off.

### Integrity and readiness

- [ ] Editorial, factual, brand, legal, privacy, and accessibility checks pass.
- [ ] Material optimization changes have approval and traceability.
- [ ] The implementation package distinguishes verified, planned, blocked, and not-applicable items.
- [ ] The baseline, measurement window, owner, and review trigger are recorded.
- [ ] No mandatory-zero issue remains.

## 47. Post-publication validation checklist

- [ ] The intended final URL resolves successfully without an unnecessary redirect chain.
- [ ] The rendered title, H1, description source, headings, content, links, media, CTA, and language match approval.
- [ ] Canonical, robots, hreflang, sitemap, and structured data reflect the intended owner.
- [ ] Old URLs redirect to the correct destination when required.
- [ ] Internal links point directly to the final canonical URL.
- [ ] Mobile, keyboard, screen-reader-relevant semantics, tables, code, forms, and interactive elements remain usable.
- [ ] Primary content is available in the rendered output expected by authorized search systems.
- [ ] Analytics and conversion events record the intended page and actions.
- [ ] Publication or migration is annotated in reporting.
- [ ] Search-platform validation and indexing status are monitored without confusing submission with inclusion.
- [ ] Enhancement or structured-data errors are triaged.
- [ ] Baseline and comparison periods are long enough and account for seasonality, campaigns, migrations, and other confounders.
- [ ] Ranking, traffic, engagement, conversion, assisted-conversion, citation, and support outcomes are interpreted separately.
- [ ] Unexpected loss has an owner, evidence log, and recovery threshold.
- [ ] The next review date or evidence-triggered review condition is recorded.

## 48. Final governing rule

The best-optimized page is not the page with the most visible SEO work. It is the page whose purpose, answer, evidence, language, structure, links, media, machine-readable signals, and next step agree so clearly that both a reader and a retrieval system can understand what the page is for, why it is trustworthy, and when it is useful.

When optimization conflicts with accuracy, accessibility, natural language, ownership, or reader value, preserve the higher-order requirement and document the trade-off. Search visibility is a distribution outcome; usefulness and integrity are the product.
